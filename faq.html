FAQ

Common setup and troubleshooting questions.

Use these answers to diagnose provisioning issues, cache behavior, and integration-test output paths.

How do I run tests directly from my IDE?

Prepare the owning module once with mvn pre-integration-test -Dlightkeeper.ide=true, then use its JUnit gutter button. See IDE setup for refresh, persistence, and troubleshooting.

Do tests share their server state?

Discovered runs use a private session per class. Ordinary methods share its process; @FreshServer restarts the process while keeping the class's world and plugin data. Other classes and later launches start from clean prepared inputs. Explicit manifest paths retain their server directory for deliberate reuse. Failed private sessions are kept for diagnosis.

Where are integration-test logs?

See Failsafe output and summaries under:

lightkeeper-integration-tests/target/failsafe-reports/

Does mvn clean verify always re-download servers?

No. clean wipes module target directories, but LightKeeper reuses jar/base-server caches under the configured cache roots (by default under your Maven local repository).

Can I supply a custom world folder?

Yes. Configure a world with sourceType=folder and a local sourcePath.

Can I add extra plugins and config files?

Yes. Put fixture JARs in src/test/lightkeeper/plugins/ and configuration files in src/test/lightkeeper/config/. Missing directories are normal. Explicit Maven, URL, Modrinth and path assets remain supported; an explicit configOverlayPath replaces the default overlay.

Can LightKeeper remove server folders after successful tests?

Yes. Use lightkeeper:cleanup-server and set deleteTargetServerOnSuccess=true. It checks failsafe summaries and only cleans on success.

How can I run the same tests on Paper and Spigot?

Configure two plugin executions and two Failsafe executions with different runtime manifest/system property values. The module lightkeeper-integration-tests demonstrates this.

Which plugin does LightKeeper install?

By default, the current module’s actual packaged Maven main artifact. For another producer, declare a test dependency and select pluginUnderTest.artifactId. Classifier and local-path overrides are available. A bad explicit selection fails; another valid JAR elsewhere is not a fallback. Existing explicit plugins configurations retain their legacy asset-only behavior until you add a target selection. See setup and migration.

Must my plugin enable successfully?

No. LK validates the archive and static descriptor metadata before provisioning. It does not require a main class to exist, the plugin to load, or it to remain enabled. Supply dependency plugins only when your test scenario needs them. Use serverOnly=true for intentional tests without a plugin under test; the LK agent itself is infrastructure.
