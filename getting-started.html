Getting Started

Your first test on a real Minecraft server.

Try a complete working project, or add LightKeeper to your existing plugin. Start with one passing test and grow from there.

Already have a plugin? Generate setup for your project and check it with doctor.

Prerequisites

  • Java 21
  • Maven 3.9+
  • Linux, macOS, or a recent version of Windows with UDS support (Windows is untested, though)

Try a working project

This independent example includes a real plugin, complete Maven configuration and a first test. You do not need to build LightKeeper itself or install its artifacts locally.

git clone https://github.com/PimvanderLoos/LightKeeper.git
cd LightKeeper
mvn -f examples/single-module/pom.xml -Dit.test=GettingStartedIT verify

Success ends with Tests run: 1, Failures: 0, Errors: 0 for GettingStartedIT and BUILD SUCCESS. The first run downloads and prepares server files; later runs reuse caches. Download and startup times depend on your computer and connection.

Ready to use your own plugin? Continue with the configuration below. For a reactor, see the separate test-module example.

1. Add one starter test dependency

Use the EldoNexus snapshot repository in both repositories and pluginRepositories: https://eldonexus.de/repository/maven-snapshots/. Set lightkeeper.version to 1.2.0-SNAPSHOT and use that version for the starter and Maven plugin. Keep your production API dependency and real packaging configuration.

<dependency>
    <groupId>nl.pim16aap2.lightkeeper</groupId>
    <artifactId>lightkeeper-junit-starter</artifactId>
    <version>${lightkeeper.version}</version>
    <scope>test</scope>
</dependency>

The starter supplies the framework, Jupiter API/engine/launcher, AssertJ and Bukkit API test types. You may still use lightkeeper-framework-junit directly when managing those dependencies yourself.

2. Bind preparation in your plugin module

LightKeeper selects the current module’s actual Maven main artifact after packaging, including an artifact replaced by Shade or Assembly. A readable JAR with valid plugin.yml or paper-plugin.yml is required before server provisioning starts.

<plugin>
    <groupId>nl.pim16aap2.lightkeeper</groupId>
    <artifactId>lightkeeper-maven-plugin</artifactId>
    <version>${lightkeeper.version}</version>
    <executions>
        <execution>
            <goals>
                <goal>lock-build</goal>
                <goal>prepare-server</goal>
            </goals>
        </execution>
    </executions>
</plugin>

Paper, the Minecraft version supported by this LK build, Java, cache paths and LK’s own versioned User-Agent have defaults. The extension stops the server process; a cleanup goal is optional.

A separate test module declares a real test-scoped dependency on its producer and selects it with pluginUnderTest.artifactId. Add groupId for an ambiguous short name, select an attached classifier, or override with an authoritative path. A failed explicit selection never falls back to another plugin. Set serverOnly=true only for intentional server-only tests.

Static validation does not load classes, require an enabled plugin, enforce runtime API compatibility, or install dependencies from plugin metadata. Missing dependencies and load failures can be intentional.

Extra JARs in src/test/lightkeeper/plugins/ and config files in src/test/lightkeeper/config/ are discovered automatically; absent directories are normal. Explicit assets remain available. An explicit configOverlayPath replaces the conventional overlay. Target/agent replacements and conflicting plugin output filenames fail clearly.

For migration, existing explicit plugins lists keep their original asset-only behavior when no pluginUnderTest is supplied. Add <pluginUnderTest/> to select the current module while retaining explicit extras, choose a producer/path, or use serverOnly.

3. Bind Failsafe and verify once

Bind Failsafe's integration-test and verify goals with failIfNoTests=true. Run mvn verify once, then use ordinary JUnit class/method launches after saving production changes. LightKeeper automatically rebuilds the current plugin through Maven; no manifest VM option or IDE flag is required. See direct JUnit and reactor setup.

For a reactor, inherit only lock-build from the parent so all producer modules acquire the early guard. Bind prepare-server only in test modules with a dependency on their producer.

Failsafe 3.6.1 uses -DskipITs for integration tests and -Dmaven.test.skip=true for all tests. -DskipTests skips unit tests; Failsafe 3.5 also treated it as an IT skip. Preparation follows effective test skips.

<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-failsafe-plugin</artifactId>
    <version>3.6.1</version>
    <configuration><failIfNoTests>true</failIfNoTests></configuration>
    <executions>
        <execution>
            <goals>
                <goal>integration-test</goal>
                <goal>verify</goal>
            </goals>
        </execution>
    </executions>
</plugin>

4. Write your first test

Save this as src/test/java/example/GettingStartedIT.java so Failsafe selects it during mvn verify.

package example;

import nl.pim16aap2.lightkeeper.framework.ILightkeeperFramework;
import nl.pim16aap2.lightkeeper.framework.LightkeeperExtension;
import nl.pim16aap2.lightkeeper.framework.PlayerHandle;
import nl.pim16aap2.lightkeeper.framework.WorldHandle;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;

import static nl.pim16aap2.lightkeeper.framework.assertions.LightkeeperAssertions.assertThat;

/** A complete first integration test; no commands or plugins from LightKeeper's internal fixtures are needed. */
@ExtendWith(LightkeeperExtension.class)
class GettingStartedIT
{
    @Test
    void placeBlock_shouldUpdateWorld(ILightkeeperFramework framework)
    {
        // setup
        final WorldHandle world = framework.worlds().main();
        final PlayerHandle player = framework.bots().builder()
            .withName("lk_tester")
            .atSpawn(world)
            .build();

        // execute
        player.placeBlock("minecraft:stone", 1, 100, 0).andWaitTicks(1);

        // verify
        assertThat(world).hasBlockAt(1, 100, 0).ofType("minecraft:stone");
    }
}

See a saved plugin change reach Minecraft

The included consumer's lkversion command reads production Java and filtered resources from its deployed JAR. This walkthrough shows the three outcomes; the commands run locally, not in your browser.

1. Original plugin and expectation: passing

SourceFreshnessIT expects the message returned by the packaged plugin.

Production response: code-v1:resource-v1:present
Test expectation:    code-v1:resource-v1:present
Result: PASS
2. Save production Java, then run JUnit: failing as expected

In ConsumerPlugin.java, change code-v1: to code-v2:. Keep the test's old expectation. Run SourceFreshnessIT directly from JUnit after the initial Maven build.

Production response: code-v2:resource-v1:present
Test expectation:    code-v1:resource-v1:present
Result: FAIL — Minecraft is running the changed production code
3. Update the test expectation, then run JUnit: passing

In SourceFreshnessIT.java, update the default expected response to code-v2:resource-v1:present. The IDE compiles the changed test as usual; LightKeeper packages the production plugin automatically.

Production response: code-v2:resource-v1:present
Test expectation:    code-v2:resource-v1:present
Result: PASS

No manual producer rebuild, runtime manifest option or LightKeeper IDE plugin is required. See the IDE guide for the supported build context and initial setup.
